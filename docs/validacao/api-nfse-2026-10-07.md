# NFS-e na integração de cobranças — 07/10/2026

A solicitação de incluir nota fiscal na mesma consulta de cobranças foi implementada com a chave de serviço existente, enviada em `X-API-Key`.

## Comportamento entregue

- A listagem e o detalhe acrescentam `nfse`: metadados fiscais, situação, número, série, verificação, chave, emissão, competência, ambiente e disponibilidade/URLs de PDF e XML. Sem nota vinculada, retorna `null`.
- `GET /api/v1/integrations/cobrancas/{billing_id}/nfse` consulta diretamente os dados da nota.
- As rotas `/nfse/pdf` e `/nfse/xml` baixam a nota emitida com XML de retorno armazenado. O PDF é gerado localmente pelo gerador de DANFSE já utilizado pelo envio por e-mail. O XML é preservado em UTF-8, sem exportar o RPS/DPS de envio.
- Os downloads exigem situação fiscal `emitida`. Nota ausente retorna `404`; não emitida, cancelada/substituída ou sem XML retorna `409` com motivo. XML inválido para gerar o PDF retorna `422`.
- A disponibilidade fiscal é independente da financeira: uma cobrança paga mantém acesso à sua nota emitida, mesmo sem boleto disponível. Cancelar financeiramente a cobrança também não cancela automaticamente a nota fiscal.
- Cobranças/clientes removidos não ficam acessíveis pelas rotas fiscais. Todas as novas rotas exigem a chave, inclusive quando existe login JWT do painel.
- A listagem obtém os metadados e o indicador de XML pela mesma consulta SQL, sem carregar documentos completos, RPS ou tentativas internas e sem consultas por nota.
- Os filtros e a paginação anteriores foram preservados. Os filtros de data continuam tratando vencimento/pagamento; não filtram data de emissão/competência. Para notas de cobranças pagas, usar `status=paga` ou `status=todos`.
- Manual Markdown 1.2, guia de comandos PowerShell/cURL e coleção Postman com 11 requisições foram atualizados. O guia inclui o comando de atualização da VPS. Os tipos da integração foram regenerados preservando os demais contratos existentes.

## Validação

Os **146 testes** de integração de cobranças/NFS-e e de geração/download de DANFSE passaram. São 70 testes anteriores da integração, 40 novos casos fiscais e 36 testes existentes de DANFSE. Foram verificados os dois formatos de XML existentes (nacional e municipal), preservação do XML, autenticação, remoções, indisponibilidade, situação financeira independente e ausência de emissão/consulta externa ou alteração da nota.

Os testes passaram no ambiente local Python 3.13.5 e na imagem `mastersat-f05-test:latest`, com Python 3.12.14 e dependências oficiais. O container executou sem rede, com backend somente para leitura e banco SQLite isolado. Evidência: `tmp/api-media-20261007/api-nfse-final.xml`. A cópia contendo apenas o backend do commit também é validada antes do push; evidência: `tmp/api-media-20261007/api-nfse-commit.xml`.

Reprodução a partir de `backend`:

```powershell
python -m pytest tests/test_integrations_api.py tests/test_integrations_nfse_api.py tests/test_nfse_danfse.py tests/test_nfse_danfse_endpoint.py -q -p no:cacheprovider
```

TypeScript passou com `node node_modules/typescript/bin/tsc --noEmit --incremental false`. Os 11 blocos PowerShell do guia foram analisados pelo parser, sem executar consultas externas. A coleção Postman foi validada como JSON e não contém chave de API. Os arquivos preexistentes acompanhados por hash foram preservados.

## Limites

Não houve implantação na VPS, emissão fiscal/bancária, consulta ao governo, envio de mensagens ou alteração de registros de produção. Os downloads dependem da nota e de seu XML já estarem armazenados no MasterSat; a leitura não recupera documentos ausentes no provedor. O PDF é uma representação local do XML fiscal, não um PDF baixado do governo. Os testes usam SQLite, não a base PostgreSQL de produção.

As URLs fiscais exigem chave: a integradora deve baixar o documento no próprio servidor e enviar o arquivo como anexo. Os PDFs antigos do manual não foram regenerados; a fonte Markdown e o guia estão atualizados.
