BE-02 — Nenhum endpoint de listagem devolve contagem total
-----------------------------------------------------------------
STATUS: CONFIRMADO, e a situação real é PIOR do que descrita
SEVERIDADE ORIGINAL: Média  →  SEVERIDADE REAL: Média-Alta (SUBIR)

Evidência verificada:
- response_model=list[ em endpoints/*.py: 31 ocorrências em 15
  arquivos — bate exatamente com o relatório.
- Não existe envelope de paginação genérico ({items, total},
  PaginatedResponse) em lugar nenhum. Os únicos campos "total*"
  encontrados são métricas de negócio (total_billed, total_received),
  não metadados de paginação.
- ACHADO NÃO CAPTURADO PELO RELATÓRIO ORIGINAL: nem todos os
  endpoints de listagem têm skip/offset. Apenas clients.py,
  trackers.py e vehicles.py têm skip: int = 0. billings.py,
  contracts.py, integration_multiportal.py, integrations.py,
  payables.py, service_orders.py têm SOMENTE limit, sem skip/offset —
  ou seja, para 7 dos 15 arquivos a paginação não é "sem total", é
  LITERALMENTE IMPOSSÍVEL pedir a página 2. nfse.py é o único com

Avaliação: o relatório subestimou o problema ao focar só na ausência
de "total"; a ausência de skip/offset em quase metade dos arquivos é
mais grave para o frontend do que a falta de contagem.

Correção recomendada: padronizar um envelope {items, total} PARA os
endpoints de maior volume, mas cobrindo os dois problemas juntos —
adicionar total sozinho não resolve nada nos endpoints que nem
aceitam skip.
Risco da mudança: médio — muda o contrato de resposta; frontend e
backend precisam ser atualizados juntos por endpoint.

Dependências: nenhuma direta, mas qualquer correção deve ser
coordenada com o frontend (páginas de listagem).

BE-04 — Log de chamada à Ailos comita a transação do chamador
-----------------------------------------------------------------
STATUS: CONFIRMADO ESTRUTURALMENTE, impacto prático hoje é hipotético
SEVERIDADE ORIGINAL: Média  →  SEVERIDADE REAL: Média (mantida)

Evidência verificada:
- _log_call (ailos_client.py:161-184) faz db.commit() na linha 184
  (não flush()), confirmado literalmente. Chamado dentro de request()
  em dois pontos: linha 702 (branch de exceção de conexão) e linha
  752 (fluxo normal).
- Busca em TODOS os call sites de ailos_client.request(...) (em
  ailos_boletos.py, ailos_pagadores.py, ailos_retorno.py): o padrão
  predominante hoje é "ler dados → chamar Ailos → só então mutar/
  persistir o resultado" (gerar_boleto, verificar_pagamento,
  solicitar_arquivo_retorno, cadastrar_pagador). NÃO foi encontrado
  nenhum call site onde mudanças pendentes relevantes já estivessem
  na sessão ANTES da chamada, dentro do mesmo fluxo de negócio. Ou
  seja: o cenário é estruturalmente possível, mas não foi observado
  em nenhum caminho atual do código — é dívida técnica latente, não
  um bug ativo comprovado.
- A COMPARAÇÃO COM _run_locked (main.py:511-534) FEITA PELO RELATÓRIO
  ORIGINAL NÃO SE SUSTENTA: _run_locked usa uma SessionLocal()
  separada e dedicada para o job de background (não a sessão de um
  request HTTP), e resolve um bug OPOSTO — antes, usar Session(bind=
  conn) na mesma conexão do advisory lock fazia o commit ser
  DESCARTADO silenciosamente (perda de dado), não "comitar cedo
  demais" nada de terceiros. São categorias de bug diferentes em
  contextos de ciclo de vida de sessão diferentes. A analogia do
  relatório deveria ser removida/reformulada.

Correção recomendada: trocar o db.commit() de _log_call por uma
SESSÃO PRÓPRIA e independente para o log — não simplesmente por
db.flush(). ATENÇÃO: se apenas trocar commit por flush sem mudar a
arquitetura, um rollback posterior no mesmo db apagaria o registro de
auditoria de uma chamada HTTP que DE FATO ocorreu — efeito colateral
que o relatório não menciona. A correção correta é replicar o padrão
que _run_locked já demonstra ser certo no projeto (sessão dedicada).
Risco da mudança: médio — muda semântica de commit em caminho
crítico (emissão de boleto); precisa de teste de integração cobrindo
falha no meio do fluxo.

Dependências: nenhuma.

BE-06 — Identidade fiscal duplicada como constantes em múltiplos arquivos
-----------------------------------------------------------------
STATUS: CONFIRMADO + achado adicional relevante
SEVERIDADE ORIGINAL: Baixa  →  SEVERIDADE REAL: Baixa-Média (SUBIR)

Evidência verificada:
- boleto_ailos.py:27-41 declara constantes de módulo hardcoded (zero
  ocorrências de "settings" no arquivo): CONVENIO="102004",
  CEDENTE_CNPJ="14228344000167", CEDENTE_NOME, CEDENTE_COD,
  CEDENTE_COD_DIG.
- core/config.py já expõe os equivalentes como settings configuráveis
  via .env: ailos_numero_convenio='102004', nfse_cnpj=
  '14228344000167'.
- ACHADO ADICIONAL NÃO CAPTURADO PELO RELATÓRIO: existe um OUTRO
  arquivo, ailos_boletos.py (nome quase idêntico — singular/plural
  trocado), que é o cliente real da API Ailos e LÊ CORRETAMENTE
  settings.ailos_numero_convenio em ~10 pontos. Ou seja, há dois
  módulos paralelos — um íntegro (lê settings) e um divergente
  (hardcoded) — e o hardcoded (boleto_ailos.py) NÃO é código morto:
  é importado ativamente por cnab240.py, cnab400.py, ailos_boletos.py,
  boleto_pdf.py, endpoints/integrations.py, endpoints/boletos.py.

Avaliação: isso não é só estética. Se o convênio/cedente mudar (troca
de cooperativa, renegociação) e alguém atualizar apenas
settings.ailos_numero_convenio via variável de ambiente, o cliente
API (ailos_boletos.py) passa a usar o novo convênio nas chamadas
HTTP, mas boleto_ailos.py continua gerando linha digitável/código de
barras/registro CNAB com o convênio ANTIGO — boletos com dados
divergentes do que está registrado, silenciosamente. Isso justifica
subir de Baixa para Baixa-Média.

Correção recomendada: fazer boleto_ailos.py ler
settings.ailos_numero_convenio etc. em vez de reconstantizar. Também
adicionar à config.py os campos que hoje não têm equivalente
(CEDENTE_NOME, CEDENTE_COD, CEDENTE_COD_DIG, AGENCIA, BANCO_CODIGO).
FAZER JUNTO com a criação de testes de CNAB (ver INT-03) para não
regredir silenciosamente — CNAB depende de boleto_ailos.py.
Risco da mudança: baixo — não exige migração de dado, mas testes que
dependem dos valores fixos (test_ailos_pdf_override.py,
test_boleto_layout.py, scripts/ailos_homologacao.py) precisam
continuar funcionando com o valor vindo de settings/env de teste.

Dependências: toca INT-03 (CNAB usa boleto_ailos.py).
